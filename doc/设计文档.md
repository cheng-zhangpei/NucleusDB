# NucleusDB: 面向多智能体记忆存储的分布式数据存储系统

[toc]

## 一、介绍

### 1. 背景与动机 (Background & Motivation)

​		随着大语言模型（LLM）能力的提升，多智能体系统（Multi-Agent Systems, MAS）正从单一的对话助手向复杂的自动化作业集群演进。然而，在将 MAS 部署至生产级的云原生环境时，现有的基于“逻辑编排”的框架面临着严峻的基础设施挑战：

**1.1 拓扑僵化与弹性缺失 (Topological Rigidity vs. Elasticity)**
		现有的主流框架（如 LangGraph, AutoGen, CrewAI）本质上专注于**应用层的逻辑编排 (Application-Level Orchestration)**。其 Agent 交互拓扑通常在启动时静态定义（Static Definition）。

- 痛点：在长周期的运维场景中，系统缺乏**运行时（Runtime）**的动态调整能力。例如，当系统负载突增需要自动扩容 Agent 实例，或需热插拔（Hot-plug）一个特定的专家 Agent 介入时，现有框架往往需要重启整个进程或预先硬编码所有可能性，无法适应云环境的动态伸缩需求。

**1.2 状态耦合与“无状态” (State Coupling vs. Stateless Architecture)**
		云原生架构的核心原则是计算节点的“无状态（Stateless）”，但智能体的本质是“强状态（Stateful）”的（依赖上下文与记忆）。

- 痛点：绝大多数框架将记忆的生命周期与智能体进程强绑定（In-Process Memory）。
  - **容灾困难：** 一旦 Agent 容器崩溃或重调度，未持久化的记忆即刻丢失。
  - **数据孤岛：** Agent A 的经验无法被 Agent B 实时读取，必须通过显式的消息传递，导致协作效率低下。
  - **继承断层：** 新启动的 Agent 无法直接挂载历史 Agent 沉淀的“经验切片”，导致系统无法实现知识积累。

**1.3 群体记忆管理的真空 (The Vacuum of Collective Memory)**
现有的记忆中间件（如 Mem0, Zep）主要设计用于增强**单个智能体与用户的交互体验**（User-Agent Interaction）。

- 痛点： 它们缺乏面向**智能体群体（Agent Swarm）**的底层原语。它们无法处理多 Agent 对同一记忆空间的高并发读写与一致性同步，难以支撑基于“黑板模式（即多个智能体共享同一记忆内容）”的高效群体协作。

​	NucleusDB 的提出，旨在探索一种**面向智能体的原生基础设施（Agent-Native Infrastructure）**。它打破了传统应用层框架的限制，通过将记忆下沉为独立的分布式存储层，实现了**计算（Agent）与存储（MemSpace）的解耦**。作为一个**研究导向的原型系统**，NucleusDB 并不试图复刻成熟工业级数据库的所有特性，而是聚焦于“存算分离”架构中多智能体协作的记忆管理。它在底层基于 Raft 共识算法构建了事务性的 KV 存储引擎，并在其上层抽象出专有的“记忆空间（MemSpace）原语，从而为构建弹性、持久、可协作的云原生多智能体系统提供了一个实验性的基座。

### 2. 核心设计理念 (Core Design Principles)

​		为了解决上述挑战，NucleusDB 确立了以下两个核心设计原则，这也构成了系统的主要技术特征：

**2.1 记忆与计算的解耦 (Decoupling Memory from Computation)**

​		与传统框架将记忆视为 Agent 进程内的私有变量不同，NucleusDB 提出 **“记忆即资源（Memory as a Resource）”** 的概念。

- **机制**：参考 Kubernetes PV/PVC 的设计模式，Agent 实例与 MemSpace 采用动态挂载（Mount/Unmount）机制。
- **优势**：这意味着 Agent 计算节点变得**“无状态”**且可随时替换，而承载认知的 MemSpace 实现了持久化与可迁移。这一设计直接解决了**1.2**中提到的容灾与继承断层问题。

**2.2 记忆总线与事件驱动通讯 (Memory Bus & Event-Driven Communication)****

​		传统多智能体系统通常依赖显式的点对点（P2P）消息传递，这导致了通信链路的复杂与脆弱。NucleusDB 创新性地引入了 **“以记忆为中心（Memory-Centric）”** 的通讯范式，将 MemSpace 升级为智能体间的**即时协作总线**。

- **机制：基于 Watch 的响应式架构 (Watch-Based Reactive Architecture)**
  NucleusDB 摒弃了低效的轮询（Polling）模式，利用底层Watch机制构建了事件分发通道。
  - **Context 抽象**：将一组协作的 Agent 封装为一个 Context，每个 Context 本质上是一个共享的通信频道。
  - **被动触发**：Agent 加入 Context 后自动注册 Watch 通道。例如，1) 当共享记忆空间（如任务黑板、状态标志位）发生变更时，变更事件会被推送（Push）给所有订阅的 Agent，瞬间触发下一步行动。2) Watcher接收到的点对点通讯请求，将会转发记忆信息。
- **优势：解耦的协作拓扑 (Decoupled Collaboration Topology)**
  这种设计实现了**发送者与接收者的解耦**。
  - **广播与单播的统一**：无论是“向特定topic运维 Agent 广播故障警报”，还是“向特定修复 Agent 指派任务”，都统一抽象为对 MemSpace 特定 Key 的写入操作（待定）。
  - **灵活组网**：Agent 只需需知道其他处于同一 Context 中的 Agent 的存在。这使得系统能够轻松实现复杂的协作模式（如发布-订阅、工作流接力），极大提升了通讯的灵活性与系统的可扩展性。

## 二、数据库内核设计与实现

### 2.1 单机数据库

#### 2.1.1 bitcask

​		[bitcask](https://riak.com/assets/bitcask-intro.pdf)是一种比较简单的键值存储架构，NucleusDB的单机存储采用bitcask作为存储引擎。数据库首先需要在内存中维护一个键的索引表，每一个键都会维护一个对应的数据项，数据项的内容包括文件ID，value的偏移，value在files中的位置，时间戳。数据库进程通过fileId即文件描述符寻找对应的数据文件。

​		Bitcask实例在文件系统上的体现为一个目录。我们将在目录中的数据文件分为了两类：活跃数据文件和非活跃数据文件。我们通过文件锁限制每次只有一个进程能进入目录，写操作只能在活跃文件上进行，这保证了IO是顺序执行的，减少了磁盘的寻址时间。当写操作到达一个阈值的时候就会将活跃数据文件追加到非活跃数据文件集合中。综上，Bitcask实例本质上是包含一个活跃可写数据文件和非活跃数据文件集合的目录。

​		每次的写入操作是追加到活跃文件之中的，删除操作实际上并不会真实的删除文件而是一个追加操作。删除操作会往文件中写入一个特殊的墓碑值，用于标记一条记录的删除即逻辑删除。由于非活跃数据文件会一直保留在磁盘中，系统没有将旧的数据物理删除，为了避免数据过度膨胀，Bitcask数据模型提出了merge的操作来删除无效数据。merge操作会遍历所有旧数据文件，将所有的数据重新写入新的数据文件中，同时删除无效数据项。merge完成之后Bitcask实例会为merge文件生成一个Hint文件。Hint文件与数据文件并没有格式上的区别，只是Hint文件中每条LogRecord的value字段并不存储value值而是value的索引。Hint文件的作用是快速构建索引，而不用去加载全部的数据文件。具体架构图如下图所示。

![img](https://github.com/cheng-zhangpei/NucleusDB/blob/0bc48c79f66b7210939d90c0d3f72df29b6318d8/image/datamodel.png?raw=true) 

> ​		因为项目跨度比较长，所以有些技术选型当时没有详细思考。Bitcask模型有一个比较有趣的特点就是内存中会维护一个比较大的所以，在不涉及CTX的远程共享内存之类的技术的时候，单机的内存往往比较有限，那么这种内存膨胀在智能体交互环境是否是可以容忍的？我认为可以，对于智能体的记忆key的占比和value（具体记忆内容）占比相比是比较小的。如果一定要考虑到内存的过大的问题可以考虑分布式数据库设计的调度和分片技术了。



#### 2.1.2 数据组织形式

​		系统在内存中需要实现一个能够支持快速插入，查找，删除的数据结构，可以选择红黑树、BTree、跳表之类的数据结构。在本系统中内存中使用跳表来组织数据，这里所使用的第三方库：Google的BTree库。为了后续可以形成较为方便的插拔模块，此处使用通用抽象接口便于后续接入其他索引类型，在系统中抽象接口被封装为Indexer结构。

​		在磁盘中的数据文件将会分为活跃数据文件和非活跃数据文件，数据库会维护当前活跃数据文件的fileId以及非活跃数据文件的fileId集合，数据文件被封装为DataFile结构，该结构将定义fileId、offset、IOManager，IOManager是系统用于管理各种IO类型的接口，目前系统共提供两种IO类型，内存映射文件IO与普通的文件IO，下为接口详细信息。

| 接口                                | 定义                        |
| ----------------------------------- | --------------------------- |
| Indexer                             |                             |
| Put([]byte, data.LogRecordPos) bool | Put：往内存索引中插入数据   |
| Get([]byte) *data.LogRecordPos      | Get: 根据key获得索引数据    |
| Delete([]byte) bool                 | Delete：根据key删除索引数据 |
| IOManager                           |                             |
| Read([]byte, int64)                 | 从文件中读取数据            |
| Write([]byte) (int, error)          | 写入字节数据到文件中        |
| Sync() error                        | 将内核缓冲区中数据持久化    |
| Close() error                       | 关闭文件                    |

数据文件中每条数据在系统中被封装为LogRecord结构，内存索引中每条数据的结构在系统中被封装为LogRecordPos。

![img](https://github.com/cheng-zhangpei/NucleusDB/blob/0bc48c79f66b7210939d90c0d3f72df29b6318d8/image/logrecord.png?raw=true) 

​		上图为logRecord编码示意图。Header头部信息包括CRC校验和，Type类型，KeySize键大小，ValueSize值大小。我们在读取数据的时候会先读取固定长度的头部Header以获取键值的大小。key Size 与Value Size字段使用变长编码转化为字节流，此处系统设置了一个Header固定读取长度（设置为15字节），反序列化时若存在多余的字节将被忽略，该设计是为了节省磁盘的空间。使用固定的长度的Header读取方式在最后一个LogRecord读取时可能发生对齐问题，此处的LogRecord的读取需从后往前的找到该末尾LogRecord的头部偏移。

> ​	在后续做智能体相关的内容时，才意识到底层的数据组织形式是可以跟着一起进行修改的，后续智能体记忆匹配是可以在底层的组织形式就进行优化的。其实可以用“Bucket”的思维在这里，将一个范围的key组织为一个桶，那么某种程度上就可以缩小在记忆匹配过程中的范围。

#### 2.1.3 数据库启动

​		数据库启动的核心有两步，1) 加载索引文件: 遍历数据文件中的所有类型的数据文件并在DB实例上注册对应的id；2) 根据数据文件或索引Hint文件创建索引。

1）主启动程序:

- step1:  对用户传入的配置文件进行校验
- step2: 判断用户传入的实例目录是否存在
- step3: 初始化DB实例
- step4: 加载数据文件
- step5: 通过数据文件加载内存索引

2）加载数据文件：

- step1: 遍历数据目录下的所有的文件，此处设计数据文件的格式为00001.data的形式
- step2: 将目录下的文件名给拆出来，构建文件ID数组
- step3: 对文件ID进行排序- step4: 区分文件中的活跃文件与非活跃文件, 注：活跃文件为ID最大的数据文件，其余为活跃文件

3）构建内存索引：

- step1: 遍历所有的数据文件中每一项LogRecord，并构建LogRecordPos及内存索引项
- step2: 判断索引项是否为被删除的墓碑值，若为墓碑值则将其从索引中删除
- step3: 更新偏移量令其指向下一个LogRecord 
- step4: 当前的文件是活跃文件，需要更新活跃文件的索引, 此处的索引是最新的索引 

注：此处仅仅为数据库启动的主体流程，随着功能的添加，单机数据库所需要启动的内容也会随之添加，现启动流程已较为复杂。详细的启动流程请阅读源码 。

#### 2.1.3 Merge数据合并机制

​		由于数据库的删除操作依然是使用添加写的方式写入墓碑值，墓碑值写入之后需要删除对应位置的索引。为了防止数据文件无限膨胀，所以需要引入merge机制将当前目录下所有的数据文件进行合并，并生成Hint文件加速索引构建。但若merge操作依然在原Bitcask实例目录，使用Put方法生成merge文件会导致merge操作与用户竞争Put锁的情况，导致系统效率降低。

​		为了解决这个问题，我们采用了下面的方法：系统使用了一个临时merge文件夹并在这个文件夹中启动了另外一个数据库实例，该实例将数据从原始的数据目录中读出之后与内存索引进行比较，如果数据有效就放入merge文件夹中。

​		在merge时，可能因为一些原因导致merge中断，所以在merge目录中添加了merge完成的标志文件，在进行merge操作之前需要先判断是否有未完成的merge操作，如果没有merge完成的标志文件说明存在没完成的merge操作。该文件中需要保存一条LogRecord，内容是记录了没有被Merge的最小的数据文件。因为在merge的过程中依然可能会有数据被添加，且需要在merge的过程中删除旧的数据文件，所以需要一个数据文件的分界线。

<img src="https://github.com/cheng-zhangpei/NucleusDB/blob/0bc48c79f66b7210939d90c0d3f72df29b6318d8/image/merge.png?raw=true" alt="img" style="zoom: 67%;" /> 

​	上图为merge操作执行的详细流程。在当前数据库实例执行merge时，需要先将当前的活跃数据文件转化为非活跃数据文件，创建目录将现在的旧数据文件复制到merge目录，此时需要创建新的活跃文件用于继续写入数据。在merge目录中，遍历当前目录的所有数据文件，将墓碑值忽略，只往Merge文件中添加正常状态的LogRecord，并且同步生成对应的索引LogRecordPos，作为value存入hint 索引文件中的LogRecord。在merge结束后，生成merge完成标志文件，merge 完成标志文件中存在一个LogRecord，记录了当前merge的最新数据文件的fileId。

​		在merge结束之后，系统需要将merge文件夹下的数据拷贝会原来的数据库目录中。并且根据merge完成标志文件的内容删除原来的数据文件。在数据库启动过程中需要进行相应修改，在进行内存索引构建过程中需要先根据Hint索引文件进行索引的构建，再对数据文件进行扫描。

#### 2.1.4 迭代器设计

​		为了用户可以更加方便的对数据进行方法，本数据库实现了基础的迭代器。我们对迭代器进行了两层的封装。1. 系统级别面向索引的迭代器。2.面向用户的迭代器。系统迭代器封装的是最基础的迭代器功能，如Next()、Rewind()等功能。而用户迭代器其实是对内存索引迭代器的进一步封装，使其对用户更加友好。在此基础上为了满足后续检索的需要，这里添加了对前缀的适配即查找的方法都要加上前缀的匹配。为了适配多种不同类型的索引类型，我们需要先定义一个统一的抽象迭代器接口以适配不同类型索引。如果使用B+树作为索引，我们需要在B+树的基础上再次对索引迭代器进行封装。

​		迭代器构建的思维是将所有的索引给放到一个数组里面，之后就可以较为简单的进行遍历。这种方法较为浪费内存，如果索引较为庞大，内存将会成倍增加。但由于索引构建使用的是Google的BTree第三方库，其中的索引暂时无法满足数据库需要，所以只能出此下策。

| Iterator                   |                                                              |
| -------------------------- | ------------------------------------------------------------ |
| Rewind()                   | 重新回到迭代器起点                                           |
| Seek(key []byte)           | 根据传入的key查找到第一个大于或者小于等于目标Key，从这个Key开始遍历 |
| Next()                     | 跳转到下一个key                                              |
| Valid() bool               | 是否有效，即是否已经遍历完所有的key                          |
| Key() []byte               | 当前遍历位置的Key数据                                        |
| Value() *data.LogRecordPos | 当前遍历位置的value数据                                      |
| Close()                    | 关闭迭代器释放资源                                           |

> 这种设计在原型是阶段是可行的，但是重新构造数组会导致内存占用翻倍，若是生产环境是不可行的。



#### 2.2.1 架构设计

​		在架构中系统参考了[etcd](https://github.com/etc1d-io/etcd)分布式键值数据库的架构设计并再次基础上进行修改与兼容调整。

> ​		为了学raft的标准实现，这个分布式的工作其实是看了好久的源码做了简化.....只是实现了基础功能很多的保障和corner case的处理被我删了.......，后面详细看了看TinyKV的教程对于很多异常的处理才会成熟些，但是现阶段最重要的任务是构建原型而不是处理corner case。

​		raft结构是raft共识算法的核心，在raft的方法中对不同状态机对于不同信息的handle方式进行了分类实现，其中Progress结构记录了该节点的运行状态现阶段主要是在日志冲突检测时起作用，用于区分Follower是否处于冲突探测状态，而ProgressTracker则是让leader可以获得集群中所有Follower的运行信息而设计的。rawnode是对raft实现功能的线程不安全的封装，message buffer算是用于暂存raft需要发送的信息，信息的发送由另外一个go routine以固定间隔发送数据。在架构中有四个通道：recevc是从网络层接受信息的通道，接受到的信息会经过r.Step()被分发到不同的处理函数。tickc: 用户传输逻辑时钟触发器所发送的时钟信号。syncc：持久化信号通道，applyc：状态机应用状态通道（这里的应用指的是Set之类的方法应用到DB本身）。

​		如图4-2，由node的部分定义可知，node结构中存在大量的通讯通道，说明在架构中对于单个的数据库节点，node主要是起到链接raft结构与外界的作用。但通道的大量设计也为本系统在海量数据场景下存在一定的问题，详情可见第六章分布式接口性能分析部分。 

<img src="https://github.com/cheng-zhangpei/NucleusDB/blob/12a4b91d02ff21d5b9f33affe8f331204775964d/image/raftNode.png?raw=true" alt="img" style="zoom: 50%;" />  

-  **Leader选举:**

​		node初始化的时候都是follower状态，每一个节点会维护一个ElectionTimeout，随机初始化为150 ~ 300ms。如果在这段时间内没有收到leader的心跳信息或者是appendEntry信息，就会转化状态机为candidate。candidate会向follower广播VoteRequest，如果他接受到多数节点的VoteResponse，就会转化为Leader。下面详细阐述一下raft主代码中Leader选举流程。

​		图为raft节点的详细架构。raft结构中会维护一个tick的函数指针，对于不同的节点状态，函数指针会指向不同的处理函数。Leader状态下节点的函数指针会指向tickHeartBeat()用于处理心跳，而candidate与follower会指向tickElection()用于触发选举逻辑，这个方法的功能是增加选举逻辑计时器electionElapse的值并与ElectionTimeout进行对比并判断是否触发选举，若触发选举，则通过Step()发送Msg_Hub类型消息通过下文的消息处理机制找到startElection()。这个方法逻辑为：1) 将自身节点状态由follower转变为candidate 2） 刷新选举间隔，若节点对象是candidate则重新开始选举周期 3）调用sendVoteMsg()广播选举信息MsgVoteRequest。

​		其他的follower节点通过消息机制收到MsgVoteRequest，将会转入handleVoteRequest处理函数，这个函数主要是修改follower的一些参数，记录投票对象并封装VoteResponse信息发送。candidate收到VoteResponse后除了在processTracker中记录收到了哪个follower的投票并且遍历processTrack中的记录判断是否超过大多数节点都进行投票，如果获得足够的票数则当前节点状态转化为leader并开始发送心跳数据。                  

- **日志添加：**

​		大体的流程就是leader接受到set、delete等操作后会先将信息放到raftlog的ent[]暂存区里面，并将日志通过消息机制发送给其他follower。当收到绝大多数节点的AppendEntryResponse信息后Leader会应用对应的日志，并且修改自身的Progress、raftlog中的apply信息。注意一下在这个过程中状态机维护的两个状态指针，committed指针指向最新的已经持久化的日志，applied指针指向已经应用到状态机的最新日志。在持久化之后才会applied，因为异步的原因，所以也不一定有强制的先后。下面站在架构的角度详细描述日志添加。

​		在node层面，在startNode()方法中会创建两个通道分别为commitc与applyc。commitc的发送方是raft代码的主循环，分别位于leader的handleEntryReponse()和follower的handleappendEntry()中。而接受端是一个application通过Listen()方法启动的go rutinue，Listen()会根据通道中的信息调用commit或者apply方法。commit的逻辑较为简单即调用数据库的PUT方法将Msg中的Entries字段传递的内容保存到数据库中。apply方法会对信息中携带的Entries进行解析，解析出对应的命令调用数据库的相关操作。

#### 2.2.2 消息机制

​		NucleusDB的raft节点之间，网络大体分为内外两层，内层是专用于raft节点之间信息消息传递的网络，使用grpc协议定义并传输消息，消息的内容使用protobuf语言封装以及消息类型如下表：

```protobuf
message Message {
  MessageType type = 1;
  uint64 to = 2;
  uint64 from = 3;
  uint64 term = 4;
  uint64 index = 5;
  uint64 commit = 6;
  uint64 rejectHint = 7;
  bool reject = 8;
  uint64 logTerm = 9;
}
enum MessageType {
  MsgHup             = 0;  // Trigger election
  MsgBeat            = 1;  // Heartbeat
  MsgProp            = 2;  // Propose log entry
  MsgApp             = 3;  // Append log entries
  MsgAppResp         = 4;  // Response to append
  MsgVote            = 5;  // Request vote
  MsgVoteResp        = 6;  // Response to vote
  MsgSnap            = 7;  // Install snapshot
  MsgHeartbeat       = 8;  // Leader heartbeat
  MsgHeartbeatResp   = 9;  // Response to heartbeat
}
```

外层使用http协议向外暴露接口，raft分布式数据库节点启动后需要使用另外的一套接口，而不是原来单机数据库的接口，对于像PUT、DELETE等对数据库数据有修改的操作，需要通过通道进行通知raft节点进行日志同步操作并且只能调用Leader节点的相关接口，而如GET操作等没有修改数据库数据的操作并不需要进行日志同步，可由任何一节点进行数据的读取。

对于raft节点对于消息处理机制如图4-5所示，每一个节点都有一个grpcServer和grpcClient，peer节点的server地址需要提前在配置文件中进行配置以便当前raft节点可以找到其他peer节点并发送数据。grpc等服务需要预先定义proto文件，在文件中声明Message类型、MessageType、消息传递服务接口定义等内容。在grpc层并不需要对消息进行筛选。

在架构中，node结构是负责网络通讯、在node启动之后，会启动两个go routine 运行grpcServer与http server。grpcServer收到消息之后通过通道将消息送入raft主循环中的Step()函数，该函数会按照消息的类型、节点的状态将信息发送给对应的处理函数。处理函数将处理好的数据封装为对应类型的消息送入消息缓冲区msg buffer。消息异步地由一个send routine调用grpcClient进行发送。

用户调用http所传入的信息在http处理函数中会封装为MsgProp提案类型，该类型的信息由node中的propc通道通过Step()传递给下层。

#### 2.2.3 冲突检测与线性一致性

​		冲突检测是为了确保分布式系统中各节点的日志能够保持一致，从而避免数据不一致或丢失的问题。为了解决这个问题，Raft 算法采用了基于日志回溯的冲突检测机制。

​		当Leader向Follower发送 AppendEntries request以复制日志时，如果Follower发现其日志与Leader的日志存在冲突（例如Follower某条日志的任期与Leader的不一致），它会拒绝该请求并返回一个 RejectHint，指示冲突发生的位置。Leader根据 RejectHint 逐步减少 NextIndex 的值，并重新发送日志条目，直到找到双方日志中第一个匹配的位置。通过这种方式，Raft 能够高效地解决日志冲突，确保所有节点的日志最终达成一致，从而维护系统的正确性和可靠性。下面举一个实现的具体例子：

​		假设Leader的日志为 [1,1,2,2,3,4]，而Follower的日志为 [1,1,2,2,2,2]，Leader向Follower发送 AppendEntries RPC，携带日志条目 {index=6, logTerm=4}。Follower检查发现自己的日志在索引 6 处的任期是 2，与Leader的日志任期 4 不匹配，因此拒绝该请求，并返回 RejectHint=6。Leader根据 RejectHint=6，将 NextIndex 调整为 5，并重新发送日志条目。Follower继续检查，发现索引 5 处的任期仍然不匹配，继续返回 RejectHint=5。Leader逐步减少 NextIndex，直到发送日志条目 {index=4, logTerm=2} 时，Follower的日志任期与Leader匹配，不再冲突。Leader从索引 4 开始，将后续的日志条目复制到Follower，最终实现日志一致。通过这种冲突检测与回溯机制，Raft 能够高效地解决日志冲突，确保分布式系统中各节点的日志最终保持一致。

#### 2.3.2 授时与时钟

​		在MVCC事务架构中，授时是很重要的一环。不同的raft节点之间本地时钟存在偏移，若节点故障触发重新选举会导致事时间链断裂，所以在架构中我们需要一个授时服务器给系统提供统一的全局时间戳，在leader选举之后重新获得全局时间戳避免时间链断裂。为了解决这个问题，我提出了混合时间戳架构，这里的混合有两层的含义，一是边缘化与中心化的混合，二是物理时钟与逻辑时钟的混合。

- 中心化与边缘化混合

​		我们采用zookeeper作为配置中心为leader分配时间租约，leader可以再时间段内进行时间戳的申请，一旦时间lease用完之后需要向zookeeper重新申请时间段lease，一旦发生了leader的选举都需要进行重新分配租约，这样设计既可以保证节点时间的时间不发生重叠也可以保证节点不需要反复的与zookeeper进行通讯从而导致大量的延迟。

​		如图5-5。ZooKeeper在此架构中扮演时间戳租约（Timestamp Lease）的协调者，具体功能如下。分配时间租约：Leader通过ZooKeeper申请一个时间戳租约，在此租约中，Leader可自主分配时间戳，无需每次请求TSO。保证时间戳唯一性：ZooKeeper通过原子操作确保不同Leader分配的时间戳段互不重叠，避免时间戳冲突。Leader容灾同步：当Leader切换时，ZooKeeper触发时间戳段回收与重新分配，确保新Leader的时间戳段与旧Leader无交集，维持全局单调递增。

![img](https://github.com/cheng-zhangpei/NucleusDB/blob/0bbc61afdd34e303a1c4f01b9848b8b85f0b8155/image/timestamp.png?raw=true) 

| 1.原子时间段分配      | 使用 CAS（Compare-And-Swap） 更新全局指针节点                |
| --------------------- | ------------------------------------------------------------ |
| 2.防止时间戳段重叠    | 通过持久节点 /global_pointer 记录最新时间戳，新Leader必须基于该值获得逻辑时钟 |
| 3. Leader故障自动回收 | 利用临时节点（Ephemeral Node）特性，Leader会话失效时自动释放其持有的租约 |
| 4. 全局单调递增       | 所有新分配的逻辑时钟必须满足：新Start = 旧End + 1（通过原子操作保证） |

- 物理时钟与逻辑时钟的混合

​		在前面的讲述中Zookeeper主要维护的是逻辑时钟，即在Leader请求TSO服务分配时间戳租约，保证节点间时钟隔断。但逻辑时钟的触发只会存在于Leader切换或是用户主动调用使得逻辑时钟前移的情况，若系统只使用逻辑时钟进行MVCC事务的维护会发生精度不足限制事务吞吐量的问题，所以需要Leader结合逻辑时钟与物理时钟生成全局混合时钟HLC。

​		HLC本质是一个64位的无符号整数，在本系统中，前十六位是逻辑时钟，由TSO进行控制，后四十八位是物理时钟，由Leader本身的本地时钟进行控制。每次Leader切换时节点将申请新的租约持有新的逻辑时钟，逻辑时钟在系统中始终保持全局递增，物理时钟则为Leader本地时钟纳秒级表示的后四十八位表示。这种设计可以在保证节点间时间戳隔断的同时兼顾本地时钟的精度。

​		使用六十四位定长时钟编码存在溢出的问题即十六位的逻辑精度与四十八位的物理精度无法表示的情况。四十八位纳秒精度的物理时钟约等于8925年，所以不可能存在溢出问题，而逻辑时钟的上限是65535，在Leader频繁切换或者数据库长时间需要保持运行的情况下溢出是有可能发生的。为了避免这种情况发生，我提供了一种事务预测调度机制。

​		该机制的大体思想如下：通过Leader切换申请租约的频率与剩余租约的数量预测租约还有多久耗尽，在事务到达临界阈值时终止该集群的事务处理功能，等待一段时间后逻辑时钟从0继续开始计时，避免出现FFFFH->0000H出现MVCC事务时间戳异常而导致冲突检测错误。

#### 2.3.3 Leader切换时的事务边界讨论

![img](https://github.com/cheng-zhangpei/NucleusDB/blob/0bbc61afdd34e303a1c4f01b9848b8b85f0b8155/image/leaderChange.png?raw=true)

​		对于混合时钟的连续性，混合时钟在节点角度看依然是逻辑时钟，但全局依然会存在一个隐性的物理时钟，在Leader切换时，虽然逻辑时钟会将Leader之间的时间戳分开，但是物理世界的时钟是依然存在，故此处需要阐述在Leader切换时是否可能会影响冲突机制而导致事务提交错乱，即时钟跳变是否会导致因果漂移。

​		如图5-6，在id为1的leader在二号事务未为Committed时奔溃，此时raft集群中的其他节点无法定期收到来自leader的心跳将会触发leader选举，此时将会新产生leader也就是id为2的节点，此时id为2的节点中的r.leader字段将会存储其上一个leader的id，在leader启动之后需要向coordinator拉取上一个leader已提交但未被committed的事务数据并在本轮leader的任期内应用事务。

​		采用混合时钟在Leader发生切换时依然会导致事务时间的断层，但这种断层并不会影响基于MVCC的分布式事务机制。对于一个Leader来说事务只会分为两种，Committed事务与Submitted事务即未Committed事务，Leader的切换只会发生在Submitted事务时间范围内，已提交事务一定在follower中成功提交了。冲突检测的本质是当前事务提交的过程中还有其他事务在这个过程中Commit从而导致一致性问题，但Leader切换之后重新提交的事务，一定不会与过去Leader提交的事务有物理时间上的重叠，因为在Leader启动时，也就是事务提交时并没有其他事务会在这个时间段Commit。

## 三、记忆空间与记忆管理

### 3.1 存算分离与架构设计

#### 3.1.1 存算分离架构

​		图检索、向量检索这类工作负载，差异不在“数据能不能存”，而在“怎么读、怎么筛、怎么算”。同一份数据落到磁盘上最终都是字节，但为了让不同查询更快，系统通常会在计算侧引入不同的**物理布局、索引与算子**：

- 向量检索更关心距离计算与 ANN 索引（例如 HNSW/IVF 等）的构建与更新；
- 图检索更关心邻接访问、k-hop 遍历、路径扩展等算子以及相应的布局优化；
- 多智能体记忆更关心高并发读写、watch 事件推送与权限隔离。

​		因此在 NucleusDB 中，我倾向于把“记忆数据的持久化”做成稳定的存储底座，而把“面向不同访问模式的处理方式（索引/缓存/算子）”放到可独立演进的计算节点中。这样同一份 MemSpace 数据可以被不同类型的计算节点以不同方式解释和加速：需要向量检索时挂载向量计算节点，需要图遍历时挂载图计算节点，需要事件驱动协作时挂载 watch/总线节点。

​		这样的设计也更复杂云原生理念，在调度时，可以通过亲和性将对应的计算节点部署到具有响应硬件能力与物理环境的节点上从而提高服务对数据处理的能力。也提高了系统的拓展性，未来也能够允许用户自定义计算节点用于对智能体的记忆甚至多模型大模型的数据计算。

​		对于智能体的通讯往往不会设计到跨越多个“路由器“的远程直连，而是每个 Agent 都能把信息传递给它认为“最相关”的邻居(Next Hop),信息最终会通过接力到达目的地，所以如何处理临近智能体的信息流动是NucleusDB智能体通讯模式的重点。我想要参照传统网络，在NucleusDB上搭建一个简化的智能体通讯网络。该网络的本质是一个基于语义寻址的去中心化服务网格

> 目前系统还没有完全将组件分离，所以这个通讯的路由方式还是比较简单的，后续的微服务拓展还要做很多适配

#### 3.3.1 Watcher机制

​		watcher的结构如下：

```go
// Watcher manages communication routing within a shared MemSpace.
type Watcher struct {
	// mu protects the routing tables
	mu sync.RWMutex
	// 1. Point-to-Point Routing Table (Physical Layer)
	p2pChannels map[uint64]chan *msg.AgentMsg
	// 2. Multicast/Topic Routing Table (Logical Layer)
	topicSubscribers map[string][]uint64
	// 3. Channel Metadata Registry (Semantic Layer)
	// Key: Topic string -> Value: Descriptor
	topicMetadata map[string]*ChannelDescriptor
	// 4. Routing Cache (Fast Path Layer)
	// Key: Content Feature Hash (or simple keyword) -> Value: Target Topic
	routeCache map[string]string
}
```

> 在原型设计阶段，所有的智能体运行在**同一个网络环境**中，在后续，在智能体解耦分不到不同的环境中需要再加上一个client的模块去进行网络的发送而不是简单的go channel的连接。

#### 3.3.2 通讯方式：从单播到语义广播

​		在 NucleusDB 的网络里，系统没有搞复杂的 IP 地址，而是设计了三种符合人类直觉的“说话方式”。智能体根据任务需求，选择不同的通讯模式：

1. **点对点单播 (Direct Messaging)**：

   ​		Agent 在输出的 JSON 中填入 `target_agent: "Agent-B"`。Watcher 查表找到 Agent B 的信道，直接把消息塞进去。这种方式最快，干扰最小。

2. **话题组播 (Topic Multicast)**：

   ​		Agent 只需要往 `target_topic: "db_maintenance"` 发消息。它不需要知道topic里具体智能体信息，Watcher 会自动把消息分发给所有订阅了这个话题的智能体。这实现了发送者和接收者的解耦。

3. **语义广播 (Semantic Broadcast)**：

   ​		Agent 将 `target_topic` 设为 `general` 或留空。Watcher（或者未来的智能路由组件）会分析这条消息的内容，看它和哪个频道的描述最匹配，然后试探性地转发过去。这就是下一节要讲的“智能路由”。

### 3.5 应用场景以及未来

**3.5.1 系统构建的目的**

​		在我本科时期，我经常被K8S烦人复杂的操作所折磨，我认为不可能所有的K8S工程师都能够很好的掌握各个中间件的调优，在我自己开发中间件比如DB的时候，也会编码大量的配置项，运维工程师我认为往往不会对这些配置项有很深刻的理解。所以在这个场景下，我认为设计一套AI系统用于接管K8S的运维或许可以减轻工程师的负担，我又设想了一个场景就是让大量智能体控制大规模的数据中心的硬件集群是一件很cool的事情。

​		如果要写一个这样的AI系统，首先面临的难题就是如何保障系统的灵活性与动态性，传统的多智能体框架由于高度的封装所导致的记忆与Agent强绑定，静态的数据流动，给复杂AI系统的构建造成了阻碍。**所以NucleusDB是旨在为复杂的多智能体或AI系统提供足够灵活、足够动态的记忆通讯管理范式。**
